# 1. Концепция

## 1.1 Идея

Проблема, которую решает Munin: обычный список задач требует, чтобы человек
сам перевёл мысль в структуру — название, срок, приоритет, категория. Это
работа, и она делается в тот момент, когда человек занят чем-то другим.
Поэтому задачи не заводятся вовсе, а потом теряются.

Munin принимает мысль как есть — текстом или голосом — и структуру достраивает
сам. «Завтра в 18 встреча с директором и надо забрать документы» превращается
в две задачи со сроками без единого поля, заполненного руками.

Отличие от обычного Todo List — два.

Первое: **ввод свободной речью, включая голос.** Не форма с полями, а фраза.

Второе, и оно важнее: **система ничего не делает молча.** Модель не изменяет
задачи — она *предлагает* действия, человек подтверждает. Предложение можно
принять целиком, частично или отклонить. Это сознательное архитектурное
решение: ошибка модели не должна приводить к потере данных.

Путь от мысли до задачи: человек говорит или пишет → (для голоса) речь
переводится в текст → текст вместе с окном его текущих задач уходит в
языковую модель → модель возвращает вызовы инструментов → бэкенд их
проверяет, фильтрует дубли и сохраняет как *предложение* → человек видит
список действий с флажками → подтверждает → только теперь меняются данные.

## 1.2 Целевая аудитория

Люди, которые хотят систематизировать свои задачи, но не готовы и не могут тратить много времени на трекеры. Кому неудобно разбираться и настраивать каждую задачу, кто хочет быстро и понятно, а также кто не может выстроить приоритеты сам

Что можно сказать по фактическому использованию: на стенде 6 пользователей и
145 задач, из них один аккаунт со 115 задачами — то есть система проверена
на реальной, а не демонстрационной нагрузке одного активного человека.

## 1.3 Пользовательские сценарии

**Сценарий A — одна задача.** Вход: «купить корм коту завтра». Система:
модель вызывает `create_task` с `title` и `deadline`, бэкенд проверяет, нет
ли уже такой задачи, сохраняет предложение. Результат: карточка «Создать —
Купить корм коту» с флажком, после подтверждения — задача со сроком на
завтра. **[РАБОТАЕТ]**, проверено живым прогоном.

**Сценарий B — несколько задач одним сообщением.** Вход: «сегодня встреча с
директором в 18, завтра забрать документы и купить молоко». Модель делает три
вызова `create_task` в одном ответе. Специальной логики разделения нет —
разделение делает модель, у неё нет ограничения на один вызов инструмента.
**[РАБОТАЕТ]**.

**Сценарий C — изменение задачи.** Вход: «перенеси встречу с директором на
завтра». Модель находит задачу в переданном ей окне контекста по ярлыку
`T1..Tn` и вызывает `reschedule_task`. **[РАБОТАЕТ]**.

**Сценарий D — изменение статуса.** «закрыть покупку корма» → `complete_task`.
**[РАБОТАЕТ]**.

**Сценарий E — изменение срока.** Отдельный инструмент `reschedule_task`,
отделён от `update_task` намеренно: перенос срока — самая частая правка, и её
стоило сделать дешёвой для модели. **[РАБОТАЕТ]**.

**Сценарий F — без слова «создай».** «позвонить юристу» — правило 3 системного
промпта: короткая фраза в инфинитиве или повелительном наклонении, которой нет
в списке активных задач, считается названием новой. **[РАБОТАЕТ]**.

**Сценарий G — двоякая команда.** Вход: «закрыть кино» при активной задаче
«кино с настей». Это может быть закрытие той задачи или новая задача с таким
названием. **[ЧАСТИЧНО, в работе]** — см. раздел 17, там подробно.

# 2. Предметная область

## 2.1 Задача

Задача — единица работы, принадлежащая одному пользователю. Поля: название
(до 512 символов), описание, приоритет, статус, срок, оценка в минутах,
группа, родительская задача, источник появления, сырой ответ модели,
признак удаления и метки времени.

Статусы: `TODO`, `IN_PROGRESS`, `DONE`, `CANCELLED`.
Приоритеты: `LOW`, `MEDIUM`, `HIGH`, `URGENT`.

Действия: создать, изменить поля, перенести срок, завершить, отменить,
удалить (мягко — `is_deleted`, строка остаётся), восстановить.

## 2.2 Сущности и таблицы

В базе 15 таблиц:

| Таблица | Назначение |
|---|---|
| `users` | учётные записи |
| `user_settings` | настройки: часовой пояс, напоминания, режим голоса, имя |
| `user_identities` | способы входа (провайдер + внешний идентификатор) |
| `login_codes` | одноразовые коды для входа по почте |
| `tasks` | задачи |
| `groups` | группы (аналог категорий), со стилем |
| `tags` | метки |
| `task_tags` | связь задач и меток |
| `recurrences` | повторяемость **[НЕ РЕАЛИЗОВАНО]** — таблица есть, логики нет |
| `reminders` | напоминания по задаче |
| `scheduled_notifications` | очередь отправки |
| `task_events` | история изменений (аудит) |
| `assistant_proposals` | предложения ассистента |
| `assistant_proposal_actions` | действия внутри предложения |
| `push_subscriptions` | подписки устройств на push (строка на устройство) |

Поля `tasks`: `id` (UUID, PK), `user_id` (UUID, FK), `group_id` (UUID, FK,
nullable), `parent_task_id` (UUID, FK, nullable), `title` (VARCHAR(512)),
`description` (TEXT), `priority` (VARCHAR(16)), `status` (VARCHAR(16)),
`deadline` (TIMESTAMPTZ, nullable), `estimate_minutes` (INT, nullable),
`is_draft` (BOOLEAN), `source` (VARCHAR(32)), `raw_llm_response` (JSONB),
`is_deleted` (BOOLEAN), `deleted_at`, `created_at`, `updated_at`,
`completed_at` (все TIMESTAMPTZ).

**Важно для главы про БД:** `recurrences` — пример того, чего в дипломе
описывать как готовое нельзя. Таблица создана миграцией `004`, но
повторяющихся задач в системе нет.

## 2.3 Связи

Один пользователь — много задач. Одна задача — **одна** группа или ни одной
(не несколько). Одна задача — много меток, через `task_tags`.

Один пользователь — много идентичностей (способов входа) через
`user_identities` с уникальностью по паре (провайдер, внешний идентификатор).
Это ключевое решение части 3: раньше `telegram_id` лежал прямо в `users`,
миграцией `015` он удалён.

Связь Telegram и основного аккаунта — не отдельная сущность: Telegram это
просто одна из строк в `user_identities`.

# 4. Функциональность

## 4.1 Авторизация

**Telegram Login** **[РАБОТАЕТ]**. Раньше через официальный виджет, сейчас
своя кнопка, ведущая на `oauth.telegram.org/auth`, с возвратом результата в
хеше адреса. Бэкенд проверяет HMAC-подпись полей ключом `SHA-256(токен бота)`
и срок годности `auth_date`.

**Telegram Mini App** **[РАБОТАЕТ]**. Внутри мини-приложения используется
`initData`, кнопка не нужна.

**Вход по коду на почту** **[РАБОТАЕТ]**. Человек вводит адрес, получает
шестизначный код, вводит его. Код хранится хэшем SHA-256, живёт 10 минут,
5 попыток, ограничение частоты запросов. Ответ на запрос кода одинаков для
знакомого и незнакомого адреса — защита от проверки чужих баз.

**Пароля нет вообще.** Ни хранения, ни восстановления. Это осознанно: нет
пароля — нет утечки паролей.

**Вход по номеру телефона** **[РАБОТАЕТ]**. Через Ucaller, но не обычным
подтверждением по коду: исходящие звонки на реальный номер владельца не
доходили — три проверки подряд (быстрый сброс, голосовой вызов, контрольный
обычный звонок с другого телефона) показали, что вызовы Ucaller теряются
между их транком и оператором, при том что их API возвращает признак успеха
и списывает деньги. Поэтому используется обратный метод `inboundCallWaiting`:
человек **сам звонит** на выданный номер, Ucaller уведомляет наш сервер
webhook'ом. Исходящий вызов заблокировать некому, и проблема доставки
исчезает как класс. Кода вводить не нужно вовсе — подтверждением служит сам
факт звонка с нужного номера.

**ВК** **[ОТЛОЖЕНО]**. План написан целиком, реализация отложена: две внешние
проверки и четыре адреса, регистрируемых на стороне ВК, при сроке работы над
проектом до конца августа. Ляжет на ту же таблицу `user_identities` без
изменения модели.

**Google, OAuth прочих** **[НЕ ПЛАНИРУЕТСЯ]** — размещать кнопки входа через
иностранные сервисы для российских пользователей запрещено (см. ниже).

**Юридический контекст, важный для диплома.** ФЗ №406-ФЗ и №199-ФЗ от
26.06.2026 запрещают авторизацию российских пользователей через иностранные
сервисы. Поэтому вход по коду на собственную почту — законен (это наш код, а
не чужая форма), а кнопку Telegram для российских адресов планируется скрывать
**[ПЛАНИРУЕТСЯ]**. Порядок обязателен: сначала у людей должен появиться второй
способ входа, только потом можно прятать первый.

Токены: JWT, есть `POST /auth/refresh`.

## 4.2 Аккаунты и интеграции

Аккаунт — запись в `users`. Способ входа — запись в `user_identities`. Один
аккаунт может иметь несколько способов; отвязать последний нельзя, проверка
на бэкенде.

**Слияние учёток** **[РАБОТАЕТ]**. Если подключаемый способ уже принадлежит
другому аккаунту, система не переносит данные молча. Возвращается `409` с
составом чужой учётки (сколько задач, групп, меток) и одноразовый токен на
10 минут; отдельный `POST /identities/merge` выполняет перенос по явному
согласию. Переносится всё: задачи, группы, метки, напоминания, история
изменений, предложения ассистента, идентичности — одной транзакцией,
повторный вызов не дублирует.

Честная оговорка для диплома: после переноса исходная учётка остаётся в
`users`, но лишается всех идентичностей, то есть войти в неё нельзя. В
диалоге это сказано прямым текстом.

## 4.3 Операции над задачами

# 5. AI-модуль

## 5.1 Модель

Сейчас: **`openai/gpt-oss-120b`** через Groq, OpenAI-совместимый эндпоинт.

История, которую стоит описать в дипломе — она показательна. Изначально

запасной путь, и обнаружилось это случайно. Отсюда вывод, попавший в план
работ: имя модели зашито в конфигурации, а решение о её судьбе принимает не
проект, поэтому нужна проверка доступности модели при старте
**[ПЛАНИРУЕТСЯ]**.

Речь в текст: **`whisper-large-v3`**, тоже Groq.

YandexGPT: код провайдера написан, в конфигурации `enabled: false`, живьём
не работал ни разу. В дипломе — **[НЕ РЕАЛИЗОВАНО]**, несмотря на наличие класса.

## 5.2 Запрос к модели

Передаётся: текущая дата, день недели, смещение часового пояса пользователя,
окно его задач (до 80 штук, ярлыками `T1..Tn`), реплика пользователя,
описания инструментов. **История переписки не передаётся.**

Полный системный промпт — в файле
`core-service/modules/assistant/assistant-impl/.../AssistantPromptBuilder.java`,
константа `SYSTEM_TEMPLATE`. Его стоит вставить в диплом целиком, он
содержательный.

Отдельно стоит описать **защиту от инъекции через данные**: реплика
пользователя приходит отдельным сообщением между разделителями, и в промпте
прямо сказано, что названия задач тоже когда-то пришли от пользователя и
инструкциями не являются.

**Короткие ссылки `T1..Tn` вместо UUID** — отдельное решение, достойное
отдельного абзаца в дипломе. Даёт экономию примерно трети входных токенов и,
что важнее, делает физически невозможным обращение к чужой задаче: ярлыков за
пределами переданного окна не существует.

## 5.10 Ошибки модели

- Неверный вызов или несуществующий ярлык → действие отбрасывается на
  валидации, причина попадает в список отказов и показывается человеку.
- Обязательное поле не указано → то же.
- Модель промолчала → запасной путь: если реплика структурно похожа на
  название задачи, предлагается создать её целиком.
- API недоступен, превышен таймаут → 20 секунд на проход, 35 секунд общий
  бюджет, дальше отказ с внятным сообщением. Есть Resilience4j.
- Пределы: 2 прохода, 20 действий, окно 80 задач, срок годности предложения
  24 часа, 10 обращений в минуту на пользователя.

# 7. Backend

## 7.2 Архитектура

**Модульный монолит плюс два выделенных воркера.** Три разворачиваемых
сервиса: `core-service` (вся бизнес-логика), `nlp-worker` (шлюз к языковой
модели и распознаванию речи), `notification-worker` (отправка напоминаний).

Почему так: микросервисы для проекта такого размера дали бы распределённые
транзакции и накладные расходы без выгоды, а чистый монолит не позволил бы
вынести обращения к внешним моделям — самую медленную и ненадёжную часть — в
отдельный процесс.

Внутри `core-service` действует **правило зависимостей**: каждый модуль
разделён на `api` и `impl`, и `*-impl` может зависеть только на чужие `*-api`
плюс общий `shared`. Это то, что удерживает монолит модульным. Хороший
пример для диплома: перенос данных между учётками задевает сразу пять
модулей, поэтому он живёт не внутри модуля, а в `core-service/app` — иначе
пришлось бы нарушить правило.

## 7.3 Модули

`assistant` — каждый парой `{api, impl}`. Плюс `shared`: `common`,

# 17. Анализ ошибок — известные, найденные живым использованием

Это самый ценный раздел для защиты: ошибки настоящие, найдены не выдумкой.

**Двоякие реплики — главная нерешённая.** При активной задаче «кино с настей»
реплика «изменить планы на кино» не даёт ничего («не нашёл, что предложить»),
а «закрыть кино» из быстрого добавления закрывает существующую задачу вместо
создания новой.

Причина оказалась в нашем коде, а не в модели: метод `looksLikeStandaloneTask`
содержал список глаголов-стоп-слов («закрыть», «изменить», «отменить»…), и
фраза, начинающаяся с такого глагола, не считалась названием новой задачи.
Список ломался тремя способами: сравнение шло по началу всей фразы, поэтому
«надо закрыть кино» его не задевало вовсе; это открытый класс, набранный
руками (есть «закрой» и «закрыть», нет «закрыл», «прикрой»); и он отвечал
одним `false` на два разных вопроса.

Решение **[В РАЗРАБОТКЕ]**: двоякость определяется разбором, а не списком
слов — по двум признакам, «читается ли реплика как название задачи» и
«насколько сильно она пересекается с существующей». При двоякости человеку
предлагаются оба варианта переключателями, и он выбирает.

Отдельно поучительно: до этого пробовали заставить модель саму сообщать о
неуверенности инструментом `mark_ambiguous` — она его не звала. Ровно так же
раньше не звала `ask_user`. Два одинаковых исхода подряд — вывод: модель
обучена отвечать уверенно, и просить её отчитаться о собственной
неуверенности значит просить о том, что она делает хуже всего.

**Прочие найденные и закрытые дефекты**, годные для раздела:

- Уведомления слали дубли бесконечно: отправка шла до пометки об отправке, а
  пометка падала на несовпадении типов (строка в колонку `uuid`).
- Интерфейс обещал то, чего система не делает — повторяющиеся задачи,
  изменение группы через ассистента, переключатель часового пояса, цвета
  групп, напоминания после закрытия задачи. Это **повторяющийся класс
  дефектов**, и он заслуживает в дипломе отдельного абзаца.
- Обратный класс: интерфейс утверждал то, чего система не знает — страница
  интеграций показывала «не подключено», пока данные грузились, и предлагала
  привязать заново при ошибке сети.
- Слияние учёток происходило молча, без согласия — исправлено.
- Склонения: «1 задач» вместо «1 задача» — исправлено.

# 21. Что готово

## Готово и работает

**Ассистент целиком:** цикл с двумя проходами, семь инструментов,
предложения с подтверждением, частичное применение, защита от дублей и от
инъекции через данные, определение двоякой трактовки, голосовой ввод.

**Задачи:** все операции, группы, метки, фокус-режим, доска с
перетаскиванием, список с фильтрами, статистика.

**Вход:** Telegram (виджет заменён своей кнопкой), мини-приложение, код на
почту, номер телефона через входящий звонок. Несколько способов на одну
учётку, слияние учёток с подтверждением и переносом данных, страница
интеграций.

**Уведомления:** Telegram, почта, push. Переключатели по каналам, защита от
состояния «ни одного канала».

**Приложение:** ставится на Windows и Android как PWA.

**Инфраструктура:** переносимость LLM-провайдера с проверкой модели при
старте, определение страны по адресу, ограничение частоты на входе, аудит
изменений.

## Готово частично

Определение двоякой трактовки — механизм работает, но срабатывает только
когда модель сама сослалась на существующую задачу (примерно четверть
случаев). Причина названа в разделе 17.

## Планируется

Вход через ВК (план написан, реализация отложена); монетизация; постоянный
домен и SSL; CI/CD; мониторинг.

# 22. Что точно НЕ реализовано

Чтобы случайно не описать как готовое:

- **Повторяющиеся задачи** — таблица `recurrences` есть, логики нет.
- **YandexGPT** — класс есть, `enabled: false`, живьём не работал ни разу.
- **SMS-уведомления** — не планируются: телефон это способ входа, не канал.
- **Вход через ВК** — план есть, кода нет.
- **CI/CD, мониторинг, постоянный домен** — нет.
- **E2E и нагрузочные тесты** — нет.
- **Пароли** — нет и не будет по замыслу.
- **Embedding и векторный поиск** — нет.
- **Пользовательские статусы** — нет.
- **Создание групп моделью** — модель выбирает только из существующих.
- **Монетизация** — нет.
- **Отдельная страница регистрации** — нет по замыслу: регистрация
  происходит при первом входе.
- **Учёт стоимости обращений.** Колонки `assistant_proposals.input_tokens` и
  `output_tokens` существуют, значения приходят от `nlp-worker` — но между
  ними нет связи, и в базу всегда пишется 0. Обнаружено при замерах
  19.08.2026, осознанно не исправлено.
- **Постраничная выборка задач в базе.** `findAllWithFilter` сочетает
  `LEFT JOIN FETCH` с постраничностью, из-за чего Hibernate разбивает на
  страницы **в памяти**, а не через `LIMIT`/`OFFSET`. На нынешних объёмах
  незаметно, но это потолок архитектуры.
- **Пометка задач, созданных ассистентом.** Колонка `tasks.source` содержит
  только `MANUAL` и `WEB` — отличить задачу, разобранную ассистентом, от
  заведённой руками нельзя. Для экспериментальной главы это стоило бы
  добавить до накопления статистики.
- **Исходящий звонок при подтверждении номера** (`initCall`) — реализован и
  оставлен за переключателем, но по умолчанию выключен: доставка не
  подтверждена, см. раздел 4.1.
- **Скрытие кнопки Telegram проверено только тестами** — живая проверка
  требует постоянного домена.

# 30. Свободный блок

Ещё у Munin есть несколько решений, которые стоит показать отдельно, потому
что они не видны из списка функций.

**Ассистент ничего не меняет сам.** Он только предлагает. Это не ограничение,
а замысел: ошибка модели не может привести к потере данных, максимум — к
отклонённому предложению. Применение бывает частичным: из пяти предложенных
действий можно принять три.

**Ярлыки `T1..Tn` вместо UUID.** Экономия примерно трети входных токенов и
невозможность сослаться на задачу вне переданного окна.

**Реплика пользователя — недоверенные данные.** Она приходит отдельным
сообщением между разделителями, и в промпте прямо сказано, что названия задач
инструкциями не являются.

**Отказ от `ask_user` и история с `mark_ambiguous`** — см. раздел 17. Это
хороший материал про пределы применимости языковых моделей.

**Снятие модели поставщиком** — тоже туда: наглядный пример того, что
зависимость от внешней модели это не только качество, но и доступность.

Наконец, стоит честно описать **метод работы**: значительная часть дефектов
найдена не тестами, а живым использованием на себе, и в журнале видно, как
одна и та же ошибка повторялась в разных местах, пока не была названа классом.
Это более убедительный рассказ, чем «всё спроектировали и реализовали».
